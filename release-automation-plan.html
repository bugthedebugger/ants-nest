Implementation proposal · review before changes

Version bump in.
Draft release out.

A GitHub Actions release pipeline for Ants Nest that detects a real package.json version increase, validates the repository, builds each native desktop target on its own operating system, bundles the CLI, and assembles one reviewable draft release.

Linux x64 · AppImage macOS ARM64 · DMG + updater ZIP Windows x64 · NSIS Standalone CLI · CJS No Intel macOS build
RECOMMENDED DESIGN

One gate, three native builds, one release assembler

Use a single workflow triggered by pushes to the default branch that touch package.json, plus a manual recovery trigger. A gate job proves that the version actually increased. Tests run once. Linux, Apple-silicon macOS, and Windows builds then run in parallel. A final job downloads an explicit allowlist of assets, creates combined checksums, and creates or refreshes a GitHub draft release.

Preflight issue found

package.json is 0.3.1, but package-lock.json currently reports 0.2.9 at the top level and 0.2.1 for the root package.

The implementation should synchronize the lockfile once, then make future mismatches a hard failure with a useful error.

Release flow

01 · TRIGGERPush to the default branch touching package.json
Manual dispatch remains available for recovery.
02 · GATERead old/new versions, validate SemVer and lockfile, reject duplicates
No build for a non-version edit.
03 · VERIFYnpm ci, typecheck, tests, production build
Release cannot bypass the normal checks.
04 · BUILD ×3Native Linux, macOS ARM64, Windows jobs
Run in parallel and upload narrowly scoped artifacts.
05 · DRAFTMerge assets, checksum, verify, create draft
Tag points to the exact version-bump commit.

Version gate: what “version updated” means

Automatic push

  • Workflow path filter: package.json on the default branch.
  • Compare the version at the push's before SHA with the checked-out commit.
  • Proceed only when the current value is valid SemVer and strictly greater than the previous value.
  • Require the root versions in package-lock.json to match.
  • Ensure no conflicting published release exists for v<version>.

Manual recovery

  • workflow_dispatch validates the current version and lockfile without requiring a prior-version comparison.
  • If a matching draft already exists, update its assets idempotently.
  • If the version is already published, stop instead of overwriting a public release.
  • Use a concurrency group keyed by version and never cancel a release halfway through.

Implementation changes

Add .github/workflows/release.yml

Default read-only permissions; grant contents: write only to the final release job. Use official checkout, Node setup, cache, and artifact actions. Pin action revisions for supply-chain stability.

Add a small release metadata script

Keep SemVer comparison, old/new version extraction, lockfile consistency, artifact allowlisting, and actionable failures testable outside YAML. Emit workflow outputs in a controlled format.

Split packaging from Linux-only preparation

Replace the current assumption that every npm run package contains an AppImage. Introduce platform-specific packaging commands or explicit Electron Builder invocations, then stage only each job's public assets.

Make architecture and names explicit

Configure Apple targets as ARM64 only, retain DMG + ZIP, configure Linux and Windows as x64, and make artifact naming collision-proof while preserving the stable names required by install.sh, install.ps1, and CLI self-update.

Assemble and verify before mutation

Download all three artifact bundles, reject unexpected/missing/duplicate files, generate a sorted checksum file, and smoke-check the standalone CLI version. Only then create or refresh the draft release and its v<version> tag at the triggering SHA.

Document the maintainer flow

Update the release notes in the README: bump with npm version --no-git-tag-version (which keeps the lockfile synchronized), push/merge, wait for the draft, review it, then publish manually.

Safety and failure behavior

Guardrails

  • No release on description/script edits to package.json.
  • No release on version decrease or malformed SemVer.
  • No draft until all tests and all native packages succeed.
  • No glob such as release/** sent blindly to GitHub.
  • No duplicate release assets from parallel jobs.
  • Draft stays invisible to “latest release” updaters until a human publishes it.

Signing is a separate credential decision

No Apple Developer or Windows code-signing secrets are present in the repository configuration inspected for this plan. The workflow can produce unsigned draft artifacts immediately, but macOS Gatekeeper and Windows SmartScreen will warn users.

The pipeline should be structured so signing/notarization can be enabled later through GitHub environment secrets without redesigning the build matrix. Secrets must never be placed in repository files.

Acceptance checklist

  • A push changing 0.3.1 → 0.3.2 starts exactly one release workflow.
  • A push editing another package.json field without changing the version exits successfully without building packages.
  • The draft is named Ants Nest v0.3.2, tagged v0.3.2, targets the bump commit, and has generated notes.
  • The draft contains an x64 AppImage, ARM64 DMG + ZIP, x64 NSIS installer, updater metadata, standalone CLI, icon, and one combined checksum manifest.
  • The CLI reports the release version when run in isolation.
  • No Intel macOS artifact or universal macOS artifact exists.
  • Publishing remains a deliberate human action after draft review.
  • A manual rerun safely repairs an incomplete draft but refuses to overwrite a published release.
